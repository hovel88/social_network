# Сервис социальной сети (курс Highload Architect)

## ДЗ 8: Разделение монолита на сервисы

### Предварительная подготовка

Была значительно переделана система сборки. Теперь в отдельный образ вынесено всё, что требуется для сборки сервисов. Ранее в Docker-файлах использовалась multi-stage сборка. Теперь стадия билдера представляет собой отдельный образ.

Для этого потребуется:

* перейти в каталог `cpp-builder/`
* выполнить скрипт `cpp-builder/prepare.sh`

По итогу соберется образ **alpine-cpp-builder:1**, со всеми библиотеками, необходимыми компиляторами, системами сборки и т.д.

Далее, нужно будет уже самостоятельно собирать образы сервисов:

* чтобы собрать сервис **social_network**, нужно выполнить скрипт `build.social_network.sh` в корне репозитория.  
В результате, с помощью образа **alpine-cpp-builder:1** будет произведена компиляция бинарника и генерация Docker-файла в каталоге `service/_build`, а далее выполнится сборка образа сервиса **social_network:8**
* чтобы собрать сервис **chat_service**, нужно выполнить скрипт `build.chat_service.sh` в корне репозитория.  
В результате, с помощью образа **alpine-cpp-builder:1** будет произведена компиляция бинарника и генерация Docker-файла в каталоге `service/_build`, а далее выполнится сборка образа сервиса **chat_service:1**

### Описание

По ДЗ нужно было выполнить декомпозицию монолитного приложения, и выделить бизнес-домен в отдельный микросервис. В качестве бизнес-домена выбран сервис диалогов (чатов).

Взаимодействие между монолитов и микросервисом реализовано на основе GRPC API, контракт которого можно посмотреть в файле `service/pb/chat_service.proto`. GRPC поддерживает несколько вариантов взаимодействия (request-reply RPC, server-streaming RPC, client-streaming RPC, both-streaming RPC), но для простоты реализации домашнего задания был выбран вариант request-reply RPC. Также GRPC поддерживает как синхронные (блокирующие) вызовы в библиотеке, так и асинхронное взаимодействие с библиотекой, но для простоты реализации домашнего задания был выбран вариант синхронного (блокирующего) взаимодействия с библиотекой. Да, выбирая варианты передачи в виде серверных стримов (для метода **ListDialogMessages** например) и используя асинхронную работу с библиотекой - можно было бы добиться значительного увеличения производительности. Но решил оставить это для рабочих задач, а не для домашней работы. А также потому, что мне требуется более глубокое изучение фреймворка GRPC.

Результатом выделения в отдельный микросервис становится:

* из монолита **social_network** вырезаем логику сервиса диалогов.  
Однако полностью "придушить" эту бизнес-логику в монолите нельзя, чтобы оставить обратную совместимость со старыми клиентами. Поэтому REST API эндпойнты `POST /dialog/([0-9a-fA-F-]{36})/send` и `GET /dialog/([0-9a-fA-F-]{36})/list` продолжают оставаться, но в их обработчиках вместо обращения к БД, происходит вызов GRPC API процедур **SendDialogMessage** и **ListDialogMessages** соответственно эндпойнтам. Т.е. в монолит добавлена реализация GRPC клиента.

* в микросервис **chat_service** переехал HTTP-сервер с реализацией REST API эндпойнтов `POST /dialog/([0-9a-fA-F-]{36})/send` и `GET /dialog/([0-9a-fA-F-]{36})/list`. А также взаимодействие с In-Memory базой Tarantool (как было реализовано в предыдущей домашней работе), вместо прямого обращения к базе PostgreSQL. Ну и реализация GRPC сервера, для обеспечения обратной совместимости со старыми клиентами, которые будут работать через монолит.

Из плюсов GRPC:

* бинарный протокол HTTP/2 с бинарными сериализованными данными в Protobuf
* ясный контракт в отдельном файле
* генерирование необходимых классов сообщений и Stub/Skeleton для сервера и клиента GRPC из контракта
* GRPC позволяет в наблюдаемость (openTelemetry), что очень здорово, и очень хотелось бы попробовать
* позволяет в хороший мониторинг, навешивать Interceptor, передавать в Prometheus метрики

Из минусов GRPC:

* сервисы автоматически становятся тяжелее на ~25МБ из-за библиотек
* сервисы автоматически становятся прожорливее по оперативный памяти на ~40МБ из-за дополнительного фреймворка
* хоть и достаточно быстрое, но дополнительное сетевое взаимодействие между двумя сервисами
* дополнительная точка взаимодействия, об отказоустойчивости которой нужно заботиться, реализовывая такие паттерны как Circuit Breaker, Retry, Bulkhead

### Подготовка

* развернуть систему

```bash
docker compose -f docker-compose.hw-08.yml up -d

# по окончании работы остановить систему командой
docker compose -f docker-compose.hw-08.yml down --remove-orphans
```

* убедиться, что таблица `dialogs` существует, для этого
  * скопировать в контейнер БД файл `misc/db_dialogs.sql`

  ```bash
  docker cp ./misc/db_dialogs.sql postgres_db:/tmp/db_dialogs.sql
  ```

  * применить файл к БД, это создаст новую таблицу **dialogs**. также будут созданы два индекса для быстрого поиска диалогов от одного к другому пользователю и для поля ключа шардирвоания (**dialogs_from_to_btree_idx**, **dialogs_to_from_btree_idx** и **dialogs_shard_key_btree_idx**)

  ```bash
  docker exec -it postgres_db psql -U postgres -f /tmp/db_dialogs.sql
  ```

Согласно постановке ДЗ:

* была проведена декомпозиция монолита с выделением бизнес-домена сервиса диалогов в отдельный микросервис.
* была проведена значительная работа по рефакторингу кодовой базы и системы сборки сервисов
